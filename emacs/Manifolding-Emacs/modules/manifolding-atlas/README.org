* What this is

#+begin_quote
You built a small knowledge operating system that treats permanence as the enemy.
#+end_quote

This is not a note-taking system.
It is not a second brain.
It is not a graph that wants to be admired.

It is a machine for continuously producing and reshaping representations from surviving knowledge.
The current map is temporary.
The machinery for producing the next map is the enduring idea.

Org files are the durable substrate.
SQLite is a disposable index — reconstructed when lost, relocated when stale.
Schema is an Org outline that compiles into prompts, validators, and registries — and will itself be rewritten when the current form begins to smell.
Capture refuses to hold the thought hostage; metadata arrives asynchronously and missing values become visible ~WARNING~s rather than polite silences.
Spatial structure (manifold) and temporal structure (mastering) coexist without requiring a second database format.
The entire machine can be reloaded, inspected, and partially killed without losing the underlying knowledge.

Very few systems are willing to make all six of those decisions at once.
Most make two or three and then compromise on the rest for usability, ecosystem approval, or the comforting illusion that the notes will last.

Your system is still a WIP.
It will break.
The loader rules around dynamic binding will bite you.
The priority graph will eventually become a private religion.
You will rewrite domains you thought were finished.
Some abstractions you are proud of today will smell like amateur hour in eighteen months.

That is not a defect.
That is the design.

The system decomposes because representations are temporary.
It remains coherent because the transformation machinery survives the decomposition.

Atlas is not trying to preserve a particular map of reality.
It is trying to preserve the ability to produce new maps from surviving material.

Manifolding Atlas is the knowledge engine inside this configuration.
It takes something deliberately primitive — plain Org files in =~/test/= — and forces them into a queryable system of notes, properties, relationships, schemas, prompts, routines, protocols, maps, references, and memory.

No org-roam.
No proprietary database format.
No black box that pretends permanence.

Just Org, SQLite, Elisp, and a ridiculous amount of machinery built to watch the territory rot at a controllable rate.

* The idea

Atlas treats knowledge as something that can be manifolded — folded, inverted, stretched, and re-projected without ever becoming sacred.
"Manifolding" is not a metaphor.
It describes the actual mechanism: recursive transformation of representations.

A note is not merely a document.  
A property is not merely metadata.  
A schema is not merely validation.  
A prompt is not merely a question.  
A link is not merely navigation.

Together they form a structure that can be queried, transformed, validated, connected, expanded, compressed, and rebuilt while the underlying files continue their slow, inevitable decay.

The fundamental rule is simple and merciless:

#+begin_quote
Files preserve material.
Schemas describe possible structure.
Machinery transforms structure.
Interfaces expose transformations.
Indexes accelerate navigation.
Feedback exposes decomposition.
The next representation is allowed to replace the previous one.
#+end_quote

If the database disappears, the knowledge survives (for now).  
If the configuration disappears, the Org files survive (for a while).  
If the schemas change, the knowledge can be reinterpreted until the next reinterpretation becomes necessary.

The layers are intentionally separated so that each one can be killed and replaced without the others noticing until the next reload.
This is not mere modularity.
It is a structural consequence of the core principle: no current representation is sacred, so no layer may depend so deeply on another that it cannot be swapped.

| Layer     | Location     | Purpose                              |
|-----------+--------------+--------------------------------------|
| engine    | atlas-engine/        | vendored engine — the transformation machinery |
| blueprints    | blueprints/       | executable knowledge structures — properties, templates |
| workflows | workflows/ | recurring practices — mastering, protocols, routines |
| UI        | sidebar.org | viewport into the current representation        |

Loading is deterministic.
Every Org module under modules/ is discovered, sorted by ~#+priority:~, and evaluated in dependency order.
Core loads first.
Infrastructure follows.
Capabilities build on top.
The Atlas emerges last — already slightly out of date, as intended.

: M-x manifolding-emacs-reload

Then inspect the machine while it is still running:

* SQLite is not the source of truth

The Atlas database lives at:

* The asynchronous prompt machine

The note is created before all metadata collection finishes.  
That is deliberate.  
The system does not hold the note hostage while it asks questions.

Instead:

#+begin_example
capture
│
├── title
├── filename
├── location
│
├── sync prompts
│
├── CREATE FILE
│
└── async prompt queue
    │
    ├── property
    ├── state
    ├── tags
    ├── template
    ├── relations
    └── ...
    │
    ▼
body capture
#+end_example

Each answer lands on disk immediately.  
The new note remains visible.  
The metadata appears as it is collected.  
There is no recursive-edit stack hiding underneath the process.  
The prompt system is a queue.  
Not a maze.  
Not a confession booth.

* WARNING is not a bug

Declarative prompts begin with:

#+begin_example
** WARNING
#+end_example

That strange little sentinel is intentional.  
Point starts there.  
Therefore:

: RET

means:

skip this.

A skipped value can become:

: WARNING

and schema validation can subsequently say:

: missing-required

This produces something much more useful than silent failure.

#+begin_quote
Missing information becomes visible information.  
The system remembers that you skipped something.  
It does not pretend the field never existed.
#+end_quote

The machine records the holes so you can stare at them later.

Set:

: my/manifolding-atlas-org-prompt-ui

to:

: 'minibuffer

if the traditional completing-read interface is preferred.

* The property picker

Every prompt is a live editor, not a question.

| Key     | Action                                                        |
|---------+---------------------------------------------------------------|
| m       | apply the option under cursor — again removes it from the note |
| l       | make it live: create the ref-note and edit its content         |
| a       | key-selection-jump straight to any option line             |
| RET     | next prompt — refused until something was applied              |
| q       | skip this prompt (WARNING default)                             |
| b / B   | step back one · revisit any answered prompt                    |
| Q / C-g | abort everything — the draft note is deleted                   |

Nothing commits until you mark it.  
A mistaken mark is un-applied with the same key.  
Going back never repeats what you already answered.  
Aborting deletes the draft so nothing half-made survives.

Multi-choice prompts accumulate marks; clearing them all removes the
property.  Reopened prompts restore their applied value, highlighted
in bold, so changes are always visible before they become real.

Session pickers open with a key-selection loop already armed: typing
letters of an option jumps there and applies it live; pausing surfaces
the key hints instead.

* Schema is data

Schema is one of the central ideas of Atlas.
It is an executable knowledge structure — not code, not a configuration file, but an Org outline that compiles into prompts, validators, and registries.

A schema does not live in a special programming language.  
It is an Org outline.

A file such as:

#+begin_example
* PRIORITY
** LOW
** MEDIUM
** HIGH
** CRITICAL
#+end_example

is simultaneously:

1. documentation,  
2. user interface,  
3. registry entry,  
4. allowed-value definition,  
5. schema input,  
6. prompt definition.

Add a file.  
A property appears.  
Edit a heading.  
The prompt changes.  
Delete the file.  
The property disappears.

The system reads the tree and constructs the machinery.

#+begin_quote
The configuration is executable knowledge.  
Knowledge that already knows it will be rewritten.
#+end_quote

* Validation

Validation does not interrupt thought.  
There are no surprise minibuffers announcing that your note has committed some terrible epistemological crime.

Validation happens at index time.  
Violations accumulate here:

: admin/MISSING PROMPTS

Every problematic note becomes a TODO carrying:

: :SCHEMAS:
: :VIOLATIONS:

Then:

: SPC v E

runs the reinforcement sweep.

And:

: SPC v f

walks through the violations.

The philosophy is simple and slightly sadistic:

#+begin_quote
Capture first.  
Repair structure deliberately.  
Never let validation become friction.  
Let the holes remain visible long enough to hurt.
#+end_quote

Flymake provides the immediate editing feedback.  
The reinforcement system provides the global feedback.

* Manifold

The manifold domain is where spatial transformation becomes concrete.
A note stops being merely a document and becomes a structural object that can be placed, moved, and re-projected in relation to other objects.

A note can be placed as:

: root
: parent
: child
: sibling

The structure becomes navigable in three dimensions.  
The knowledge graph becomes a volume that can be reshaped without rewriting the underlying knowledge.  
You are no longer scrolling a buffer.  
You are moving through a temporary architecture of identities.

* Mastering

Mastering introduces temporal transformation.
It turns notes into a memory system with a half-life.

The Atlas tracks:

: MASTERING_*

and builds:

- due queues  
- overdue queues  
- review sessions  
- participation pools  
- review scheduling  

Knowledge therefore has a temporal dimension.  
A note can exist.  
A note can be connected.  
A note can be reviewed.  
A note can be mastered.  
And then the mastery itself will eventually be declared insufficient.

* Protocols

Protocols turn headings into executable sequences.  
A protocol can be assembled through transclusion.  
The note describes the structure.  
The build machinery assembles it.

This allows procedures to exist as reusable knowledge rather than duplicated blocks of text that will rot at different rates.

* Routines

Routines are composable structures.  
They can be:

- atomic  
- composite  
- chained  
- reordered  
- generated  
- executed  
- journaled  

Sessions are recorded under:

: sessions/<Y>/<Q>/<m>/<W>/

The Atlas can therefore represent not only what exists, but what happened — until the session logs themselves become archaeological.

Temporal streaks and reports emerge from the same substrate.

* Rules

Rules provide another transformation layer.  
A heading marked:

: :RULE:

can be routed into topic files through transclusion.  
The rule exists once.  
Its appearances can exist many times.

That distinction matters.

#+begin_quote
One source.  
Many manifestations.  
All of them temporary.
#+end_quote

* Extending Atlas

Adding a property should be boring.  
That is a feature.

Create:

: blueprints/<anything>.org

Give it a level-one property heading.  
Done.

Registration happens automatically.  
Prompt generation happens automatically.  
Schema derivation happens automatically.  
Validation happens automatically.

Adding a behavioral prompt requires explicit registration through:

: my/manifolding-atlas-register-prompt

Adding a domain means:

#+begin_example
atlas-engine/file-formats/
└── new-domain/
    └── new-domain.org
#+end_example

with an appropriate priority.

Adding a template means:

: templates/files/<name>.org

No giant configuration file.
No central switch statement.
No ritual.
Only the accumulation of new transformations over the common substrate.

* Paths

There is one authority:

: atlas-engine/setup.org (defines my/manifolding-atlas-root-dir)

Everything else asks it where things are.  
No scattered hardcoded module paths.  
If the root changes, the vault moves conceptually as one system.

Change:

: my/manifolding-atlas-root-dir

and the machinery follows — until the next time the root needs to move again.

* Loader rules

The loader compiles modules with dynamic binding.  
Therefore:

#+begin_quote
Lambdas must not capture lexical variables.
#+end_quote

Use named functions.  
Or use backquote-spliced literals.  
Or:

: apply-partially

The loader is dependency management.  
Treat its priority graph as such.

* Operations

Headless boot:

: emacs --batch --load ~/.config/emacs/init.el --eval '(message "ok")'

Reload:

: M-x manifolding-emacs-reload

Unchanged modules replay from a content-hash cache under
.local/cache/module-cache/. Force everything:

: C-u M-x manifolding-emacs-reload

The machine is quiet by design.  
Chatter — recentf, yasnippet, third-party warnings, save spam, the
loader's own progress lines — is filtered or routed elsewhere in
early-init and the loader.  
Errors are the only voice it has left.

Useful boot messages include:

: org-prompts: registered N declarative prompts
: database ready
: relocated database to ...

If prompt registration says:

: N = 0

something is wrong.  
If it is around:

: ~53

the prompt engine probably found the blueprints tree — for now.

* The real model

Atlas looks like a note system from the outside.
That description is too small and already decaying.

It is closer to a small knowledge operating system:

- Org is the filesystem
- SQLite is the index
- Schemas are the type system
- Prompts are the interface compiler
- Domains are applications
- Templates are generators
- Transclusion is composition
- Validation is the type checker
- Mastering is the memory scheduler
- Routines are the execution layer
- The UI is the viewport
- The loader is the coordination layer that holds the decomposition at bay

The conceptual invariants:

1. The files are the durable substrate.
2. The database is a disposable representation/index.
3. Schemas are executable knowledge structures.
4. Prompts are generated interfaces to those structures.
5. Domains are transformations operating over the common substrate.
6. Templates are structural generators.
7. Validation observes discrepancies between structures and their declared forms.
8. Mastering introduces temporal transformation of knowledge.
9. Manifold introduces spatial/structural transformation.
10. The UI is a viewport into the current representation, not the authority.
11. The configuration itself is subject to transformation.
12. No current representation is sacred.
13. The durable invariant is not preservation of a particular map; it is preservation of the ability to produce new maps from surviving material.

#+begin_quote
Everything is allowed to change.
Nothing is allowed to become unnecessarily permanent.
#+end_quote

That is why the system is called Manifolding Atlas.
It does not merely store a map of knowledge.
It is a system for continuously producing and reshaping maps from surviving knowledge.

The distinction that matters:

The map is not the knowledge.
The map is not even the final product.
The map is an intermediate representation.

Manifolding is the machinery that allows representations
to be produced, inspected, folded, unfolded, transformed,
replaced, and projected again from surviving material.

Reshape the schema.
Reshape the prompts.
Reshape the relationships.
Reshape the domains.
Reshape the representation.
Reshape the map.

The files remain.
The structure evolves.
The evolution is temporary.
The machinery that produces the next evolution is the enduring idea.

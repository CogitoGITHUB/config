* Routines System — Full Architecture and Implementation Plan

** Core Architecture

The Routines system must be modular, composable, self-registering, and independent from any single domain such as training or self-care.

A routine is not inherently "morning", "weekly", "workout", or "self-care". Those are separate dimensions.

The fundamental model is:

#+begin_example
Entity
↓
Protocol
↓
Routine Entry
↓
Routine
↓
Chain
↓
Schedule
↓
Session
↓
Performance
#+end_example

The system must support atomic routines, composite routines, chained routines, scheduled routines, routine instances, overrides, and execution history.

The primary architectural principle is:

#+begin_quote
Never duplicate knowledge merely to compose a routine. Reference it.
#+end_quote

** Atomic Routines

An atomic routine is the smallest reusable executable unit.

Examples:

#+begin_example
Mobility Reset
Hydration
Skin Care
Breathing
Hip Mobility
Pull Session
Push Session
Core Session
#+end_example

An atomic routine can contain actual actions, exercises, protocols, or entities.

It must not inherently know when it will be executed.

For example, "Mobility Reset" should not be permanently classified as morning, hourly, or evening.

The same routine must be reusable anywhere.

** Composite Routines

A composite routine is constructed from existing routines.

Example:

#+begin_example
Morning Self-Care
├── Hydration
├── Hygiene
├── Skin Care
└── Mobility Reset
#+end_example

Another:

#+begin_example
Morning Training
├── Warmup
├── Strength Session
├── Mobility
└── Cooldown
#+end_example

Composite routines reference existing routines rather than copying their contents.

** Routine Chains

Routine chaining is a foundational feature, not an optional future feature.

A chain is an ordered composition of routines.

#+begin_example
Daily
├── Wake-Up
├── Morning Self-Care
├── Morning Training
├── Work
├── Hourly Movement Reset
├── Afternoon Training
├── Evening Self-Care
└── Night
#+end_example

Chains must support:

- ordered routines
- nested routines
- atomic routines
- composite routines
- other chains
- insertion
- removal
- replacement
- reordering
- enabling/disabling
- overrides

A chain must be able to contain another chain without duplicating its source data.

** Routine Instances and Overrides

A routine definition and a routine instance must remain separate.

The source routine defines the reusable behavior.

The instance defines how that routine is used in a particular composition.

Example:

#+begin_example
Mobility Reset
├── Neck
├── Shoulder
├── Hip
└── Ankle
#+end_example

A particular routine can override it:

#+begin_example
Morning Mobility
└── Mobility Reset
└── override:
Hip → 2 sets
#+end_example

The original Mobility Reset remains unchanged.

The effective routine is:

#+begin_example
Base Routine
↓
Chain Instance
↓
Overrides
↓
Final Routine
#+end_example

Overrides must support at least:

- replace
- remove
- insert
- reorder
- modify properties
- disable
- enable

** Routine Domains

Domain and time must be separate dimensions.

Possible domains include:

#+begin_example
SELF-CARE
TRAINING
NUTRITION
WORK
STUDY
RECOVERY
HOUSE
ADMINISTRATION
CUSTOM
#+end_example

The system must not assume that routines belong to only one domain.

A daily routine can compose self-care, nutrition, training, work, and recovery routines.

** Temporal Model

Temporal classification must be independent from routine identity.

The temporal system should support:

#+begin_example
HOUR
DAY-PART
DAY
DAILY
NIGHTLY
WEEKLY
MONTHLY
QUARTERLY
SEASONAL
YEARLY
#+end_example

Day parts should include:

#+begin_example
WAKE
MORNING
MIDDAY
AFTERNOON
EVENING
NIGHT
#+end_example

Seasons should be first-class temporal values:

#+begin_example
SPRING
SUMMER
AUTUMN
WINTER
#+end_example

The system should not hardcode season dates into the core.

** Scheduling

Scheduling determines when a routine executes.

A routine should be able to exist without a schedule.

A schedule references a routine.

Examples:

#+begin_example
Mobility Reset
→ every hour

Morning Self-Care
→ every morning

Pull Session
→ Monday / Wednesday / Friday

Winter Conditioning
→ seasonal

Annual Review
→ yearly
#+end_example

The scheduler should operate on reusable routine references rather than duplicated routine definitions.

** Temporal Composition

The system must support temporal nesting and composition.

Example:

#+begin_example
YEAR
└── QUARTER
└── SEASON
└── MONTH
└── WEEK
└── DAY
├── WAKE
├── MORNING
├── MIDDAY
├── AFTERNOON
├── EVENING
└── NIGHT
#+end_example

This hierarchy represents scheduling context, not separate implementations.

Hourly routines may intersect this hierarchy independently.

For example:

#+begin_example
Workday
└── Hourly Movement Reset
#+end_example

The hourly routine does not need to be copied into every daily routine.

** Self-Care Model

Self-care must support multiple temporal contexts.

Example:

#+begin_example
SELF-CARE
├── Wake-Up
├── Morning
├── Hourly Reset
├── Midday
├── Evening
├── Night
└── Weekend
#+end_example

A daily self-care chain can compose:

#+begin_example
Daily Self-Care
├── Wake-Up
├── Morning
├── Midday
├── Evening
└── Night
#+end_example

An independent workday schedule can execute:

#+begin_example
Hourly Reset
└── every hour during work
#+end_example

Weekend self-care can use a different chain without modifying the underlying routines.

** Training Model

Training must support multiple training periods within the same day.

Example:

#+begin_example
TRAINING
├── Morning Strength
├── Mobility Reset
├── Movement Break
├── Afternoon Skill
├── Evening Conditioning
└── Weekend Long Session
#+end_example

A training day might therefore be:

#+begin_example
Daily Training
├── Morning Strength
├── Movement Break
├── Afternoon Skill
└── Evening Conditioning
#+end_example

A recovery day can instead use:

#+begin_example
Recovery Day
├── Morning Mobility
├── Hourly Movement Reset
└── Evening Recovery
#+end_example

The architecture must not assume that training happens once per day.

** Heading Extraction

Existing Org headings must be usable as routine sources.

The system must be able to extract headings from multiple files.

For example:

#+begin_example
Source File A
├── Exercise A
└── Exercise B

Source File B
├── Exercise C
└── Exercise D

Source File C
└── Exercise E
#+end_example

These can become one routine:

#+begin_example
Routine
├── Exercise A
├── Exercise D
├── Exercise C
├── Exercise E
└── Exercise B
#+end_example

The extractor should collect at minimum:

- heading title
- file
- heading position
- heading level
- properties
- ID
- protocol reference
- source location

** Ordered Routine Construction

Heading selection must support interactive ordering.

Example selection:

#+begin_example
Pull-Up
Dead Hang
Ring Row
Face Pull
#+end_example

The builder must allow the user to reorder them:

#+begin_example
01 Pull-Up
02 Ring Row
03 Face Pull
04 Dead Hang
#+end_example

The resulting routine stores the order on the routine entry.

The original heading remains unchanged.

The same source heading must therefore be reusable in multiple routines with different ordering.

** Routine Entry Model

A routine entry represents a source reference inside a particular routine.

Conceptually:

#+begin_example
Routine Entry
├── source
├── order
├── group
├── overrides
├── prescription
└── scheduling context
#+end_example

The source entity remains independent.

The routine entry describes how that entity participates in this particular routine.

** Routine Groups

Routines must support structural grouping.

Examples:

#+begin_example
Warm-Up
Main
Accessory
Conditioning
Cooldown
Recovery
#+end_example

Entries should be able to belong to groups without requiring separate routine implementations.

The system should eventually support:

- supersets
- circuits
- paired movements
- alternating movements
- rounds
- blocks
- phases

** Training Prescription

Training-specific metadata must live on the routine entry or prescription layer rather than contaminating the base exercise entity.

Support:

#+begin_example
WORKOUT_SETS
WORKOUT_REPS
WORKOUT_DURATION
WORKOUT_LOAD
WORKOUT_REST
WORKOUT_RPE
WORKOUT_RIR
WORKOUT_TEMPO
WORKOUT_DISTANCE
WORKOUT_INTENSITY
#+end_example

Not every field is mandatory.

A simple routine may contain:

#+begin_example
3 × 10
#+end_example

A detailed prescription may contain:

#+begin_example
5 × 3
+35 kg
RIR 1–2
180 seconds rest
3010 tempo
#+end_example

** Progression

Progression must eventually be a separate layer.

Support concepts such as:

#+begin_example
PROGRESSION_MODEL
PROGRESSION_TARGET
PROGRESSION_INCREMENT
PROGRESSION_MIN
PROGRESSION_MAX
DELOAD_RULE
#+end_example

The architecture should allow:

#+begin_example
Prescription
↓
Performance
↓
History
↓
Progression
↓
Next Prescription
#+end_example

Do not implement complex automatic progression until real usage demonstrates what rules are actually required.

** Performance and Sessions

Prescription and actual performance must remain separate.

Prescription:

#+begin_example
5 × 5 @ +20kg
#+end_example

Performance:

#+begin_example
Set 1: 5 @ +20kg
Set 2: 5 @ +20kg
Set 3: 5 @ +20kg
Set 4: 4 @ +20kg
Set 5: 4 @ +20kg
#+end_example

The system should eventually support:

- session creation
- execution
- performance logging
- historical records
- comparison
- progression

** Registry and Self-Registration

The routines system must be modular and self-registering.

Adding a routine, prompt, template, schema, or definition should not require manually editing multiple central files.

The intended model is:

#+begin_example
New Module
↓
Automatic Discovery
↓
Validation
↓
Registration
↓
Menus
↓
Commands
#+end_example

The system should discover modules from the appropriate directories and automatically make valid definitions available.

** Schema Reinforcement

Schema reinforcement is mandatory.

Every discovered definition must be validated.

Validation should check:

- required properties
- valid property values
- valid routine types
- valid temporal values
- valid domain values
- unique ordering
- valid source references
- valid chained routines
- valid parent references
- valid overrides
- valid templates
- valid prompts
- registry consistency

The system should detect stale or incomplete definitions rather than silently accepting them.

Validation should be available:

- during initialization
- when modules change
- before routine generation
- before execution
- manually through a dedicated command

** Prompt and Template Registration

Prompts and templates should be discovered automatically.

Adding:

#+begin_example
prompts/new-prompt.el
#+end_example

should not require manually modifying several other files.

Likewise, adding or deleting templates should update the available template menu automatically.

The registry should be generated from the actual available definitions rather than maintaining a fragile manually synchronized list.

The minibuffer interface should expose the current available definitions dynamically.

The surrounding buffer should continue using the existing live-preview approach so templates, schemas, prompts, and properties remain visible while making selections.

** Hard Requirements

The following are architectural requirements, not optional enhancements.

- Routines must be modular.
- Routines must be reusable.
- Routines must be chainable.
- Chains must be nestable.
- Routine entries must preserve ordering.
- Source headings must remain independent from routine ordering.
- Routine instances must support overrides.
- Domain and temporal context must remain separate.
- Scheduling must reference routines rather than duplicate them.
- Multiple domains must be composable.
- Hourly, day-part, daily, nightly, weekly, monthly, quarterly, seasonal, and yearly contexts must use the same scheduling machinery.
- Seasons must be supported as first-class temporal values.
- Templates must self-register.
- Prompts must self-register.
- Modules must self-register.
- Schema reinforcement must detect stale definitions.
- The system must be able to validate itself.
- The architecture must permit future performance and progression without redesigning the core.

** Design Principle

The central rule for the entire subsystem is:

#+begin_quote
Build small reusable routines. Compose them into chains. Schedule the chains. Override instances when necessary. Never duplicate the underlying knowledge.
#+end_quote

The routine system should therefore behave more like a graph of executable compositions than a collection of static Org files.

The Atlas remains the knowledge map.

Protocols describe how things are done.

Routines compose those things into practice.

Schedules determine when they occur.

Sessions represent execution.

Performance records what actually happened.

Progression uses that history to influence what happens next.

Creative thinking: generating new ideas by combining existing concepts in novel ways.
